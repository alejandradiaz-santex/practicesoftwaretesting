# BUG-002: [Checkout/Billing] Código postal inválido (ZZZZ) aceptado y autocompletado con datos ficticios

## Datos generales

- **Severidad**: Media
- **Prioridad**: [FALTA DATO: la define el PO]
- **Ambiente**: prod — https://practicesoftwaretesting.com (demo pública)
- **Versión**: v2.5, build 2026-10-11 (pie de página); el título dice "Toolshop - v5.0" (leído el 2026-10-27)
- **Navegador / dispositivo**: Firefox 157.0 y WebKit 27.2 (Playwright 1.64.1) en Windows 11; capturas manuales en Chrome 156.0.8078.48
- **Ticket relacionado**: TC-005
- **Reportado con**: QATES (qa-ops)

## Qué pasó

Al escribir un código postal que no existe ("ZZZZ"), el sitio no avisa del error: rellena la dirección con datos inventados y deja continuar al pago. Una dirección no validada puede llegar a la factura (no verificado).

## Pasos para reproducir

**Precondiciones**: producto en el carrito y compra como guest hasta el paso Billing Address.

1. Elegir el país AR.
2. Escribir el código postal `ZZZZ` y el número de casa `123`.
3. Esperar a que termine la consulta de dirección.

**Resultado esperado**: un mensaje de error de código postal y el botón para continuar deshabilitado — según el propio sitio, que rechaza `ZZZZ` con un 422 para otros países (DE y NL); no hay criterio de aceptación escrito

**Resultado obtenido**: `GET /postcode-lookup?country=AR&postcode=ZZZZ&house_number=123` responde 200. Street, city y state se autocompletan con valores ficticios (los genera Faker; son los mismos para el mismo país y código), no hay mensaje de error y `proceed-3` queda habilitado.

**Frecuencia**: Siempre (10 de 10 intentos en Firefox y 10 de 10 en WebKit, 2026-10-24)

## Origen

- **Cómo se encontró**: exploración real del agente planner de Playwright el 2026-10-20 (`specs/checkout.md`, commit eca6171); validado por qa-ops el 2026-10-22 sin reproducción en vivo; reproducido manualmente el 2026-10-27 (00:49:04 GMT, Chrome)
- **Capa**: API: `/postcode-lookup` acepta el código porque el país no tiene regla de formato
- **Dónde falla**: `GET /postcode-lookup` → 200 (trace id: no se observa en las cabeceras de respuesta capturadas) | pantalla Billing Address › código postal
- **Desde cuándo**: La búsqueda sin validar el formato existe desde 2026-04-18; desde 2026-06-10 se valida para 27 países (ver Fuente del error). Build actual: 2026-10-11, anterior a la primera observación (2026-10-20); no se verificó si hubo redespliegues. Última versión sin el bug: no se conoce

## Impacto

- **Qué flujo afecta**: dirección de facturación en el checkout
- **A quién afecta**: Visitantes sin cuenta (guest) con un país sin regla de formato (comprobado con AR y AD); los 27 países con regla rechazan el código (comprobado con DE y NL)
- **Cuántos**: N/A: sitio demo, sin usuarios reales ni métricas de uso

## Fuente del error (Nivel 2)

- **Archivo y clase**: `sprint5/API/app/Services/Postcode/PostcodeFormat.php:65-71` › `PostcodeFormat::matches`, llamado desde `PostcodeController::lookup`. Los datos ficticios los genera `FakerPostcodeDriver::lookup`. Está en el repo del sitio, no en este proyecto.
- **Commit o PR que lo introdujo**: `62f440d` (2026-04-18, PR #776): búsqueda sin validar el formato. `b8255fe` (2026-06-10, PR #809): validación solo para 27 países, sin Argentina.
- **Cómo lo encontraste**: 1) **Trace Viewer de Playwright** (TC-005), pestaña Network: `GET /postcode-lookup?country=AR&postcode=ZZZZ&house_number=123` → 200 con una dirección ficticia; 2) búsqueda de `postcode-lookup` en el repo del sitio y lectura de `PostcodeController`, `PostcodeFormat` y `FakerPostcodeDriver`; 3) cuatro `GET` de solo lectura al sitio: AR y AD → 200, DE y NL → 422.
- **Causa**: `matches()` devuelve `true` para los países que no están en `PATTERNS` (solo 27 tienen regla), y el backend responde con una dirección ficticia de Faker. Evidencia: traza, código y las cuatro consultas.
- **Certeza**: Confirmada
